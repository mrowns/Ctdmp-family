Date: 27 October 2026

Environment: isolated ctdmp_test, local loopback API/worker, headless Chromium
Provider modes: YouTube MOCK; WhatsApp DRY_RUN; external browser navigation intercepted.

Implemented:
- Migration 014 stores eight random 256-bit single-use recovery code digests per member; raw codes are returned only for one-time display.
- Generating a replacement set invalidates older unused codes.
- Recovery accepts a normalized organization-scoped username plus one code. Unknown usernames and invalid/replayed codes share a generic rejection.
- A persistent bucket limits each browser token to eight attempts per 15-minute window; one-day-old buckets are removed by bounded worker retention.
- Successful recovery invalidates the full code set, revokes existing member sessions, records an audit event without secrets, and issues a 12-hour session with no credential binding.
- A recovered member can register a replacement passkey through the existing recent-authentication flow.
- Recovery uses a standard HTML form and works without JavaScript.

- pnpm check: TypeScript passed; 31 PostgreSQL/API tests passed, 0 failed or skipped.
- pnpm test:browser: 20 Chromium checks passed, including recovery, session revocation, replacement passkey enrollment and discoverable sign-in.

Limitations:
- No production recovery policy, distributed/IP abuse controls, verified WhatsApp recovery, public signup, production RP domain, native ceremony or physical-device validation.

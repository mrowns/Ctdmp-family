# Decisions

- ADR-001: VPS development is authorized by the owner's later instruction; local workspace holds private SSH control memory only. Application changes and execution happen on VPS.
- ADR-002: One-host development deployment; PostgreSQL 17 and Redis 7 in memory-bounded Docker containers, loopback ports and persistent volumes. Mutable minor image tags will be pinned by digest before release.
- ADR-003: Drizzle selected instead of Prisma under specification section 19's permitted alternative. Use typed Drizzle SQL/repositories progressively; financial claims, locks and advanced constraints use reviewed PostgreSQL SQL. Current queries use node-postgres directly within the shared transaction helper; expanding typed repositories remains a task, not a claimed completed migration to ORM modeling.
- ADR-004: API and worker bind to no public application endpoint. APP_ENV other than local/test is rejected while fixture authentication exists. No real provider mode is accepted.
- ADR-005: Fictional budget uses TEST integer units; ledger entries are simulated reservations and never provider costs. Dry-run outcomes are DRY_RUN_PREPARED, not delivered.
- ADR-006: AES-256-GCM protects recoverable delivery payload; join table stores only SHA-256 digests of 256-bit tokens. Key is generated server-side in ignored environment. Current payload retention/rotation is incomplete and blocks launch.
- ADR-007: Unit database and demo database are separate. Test results reference only executed scenarios, not full source requirement compliance.
- ADR-008: Proposed web stack remains Next.js App Router/Tailwind. No website hosting service or public publication has been activated.

- ADR-009 (25 October): The first browser slice uses Fastify-served semantic HTML in `apps/web/src/pages.ts`, sharing the same origin and server authorization as the API. It requires no JavaScript, additional web server, or client token storage. This is an interim frontend, not completion of the proposed Next.js/Tailwind architecture. Next.js remains follow-up work; domain contracts stay framework-independent.
- ADR-010: Development browser sessions may use operator-issued opaque, digest-stored fixture access codes or the explicitly labeled local/test passkey signup. Neither path grants roles or administration. Codes expire after one hour; member cookies are HttpOnly/SameSite=Strict and server-revoked on logout. These HTTP loopback cookies are not production sessions. Non-local/test environments remain rejected.
- ADR-011: BullMQ queue prefixes include environment and database name to isolate database-backed notification IDs across development and tests. Database records remain authoritative. Browser tests use ctdmp_test, port 3200, their own worker, and intercepted external browser navigation.
- ADR-012: Keep `Referrer-Policy: no-referrer` on personal pages. Chromium form POSTs can serialize Origin as null under that policy; accept this only with same-origin Fetch Metadata, the expected loopback Host, and the browser-bound CSRF token/join nonce. Explicit cross-site requests remain rejected. CSP form-action permits self and the constructed YouTube destination, because Chromium applies the form policy to redirect targets too.

- ADR-013 (26 October): Public Home/resolution uses an explicit organization-scoped program selection with its own revision; local_date and title never select an intended live session automatically. The selected session is always shown first in the control room.
- ADR-014: Program-management and sending changes require separate global grants, a recently verified fixture session (15 minutes), reasons and optimistic revision checks. Shared database services enforce this for JSON and browser commands, with locks that serialize grant revocation and sender pause boundaries. This does not replace launch-required strong administrator authentication.
- ADR-015: Workers and administrators lock program before observation. Completed sessions are terminal; same-video recovery preserves its stream sequence. Rejected videos remain blocked automatically until a deliberate fresh approval. State transitions and safe evidence are append-only application records; legacy history is not invented.
- ADR-016: Interactive scenario controls are restricted to mock-only local/test fixtures, explicit demo/program grants and recent sign-in. Creation is idempotent and preserves prior sessions; observation injection accepts only sessions created by that workflow. Own test-alert pages are private to the fictional recipient.
- ADR-017: Mock joining destinations are local demonstration pages rather than real YouTube requests. Live provider mode remains unavailable. CSP returns to self-only form targets; any future real YouTube redirect policy must be activated and browser-tested with its actual adapter.

- ADR-018 (27 October): Use SimpleWebAuthn server/browser v14 packages for passkey ceremonies. Keep the expected origin and RP ID explicit; local/test defaults are localhost, and APP_ENV outside local/test remains blocked. Store credential public data, digest-only opaque sessions and browser-bound single-use challenges. Do not claim production auth or device support from virtual-authenticator tests.
- ADR-019 (27 October): Permit self-registration only in local/test. New members remain inactive until their first discoverable resident passkey verifies with user verification; username uniqueness is organization-scoped; default alert preferences are off; pending accounts expire. No signup receives a branch or role. Production signup, consent text, recovery, abuse controls and RP/domain policy require separate completion and approval.
- ADR-020 (27 October): Local/test recovery uses eight random 256-bit single-use codes stored only as SHA-256 digests. Rotation invalidates previous codes. Successful recovery revokes existing member sessions and all outstanding recovery codes, then issues a short-lived session that can register a replacement passkey. Limit attempts to eight per browser token per 15 minutes and clean old buckets after one day. This is development evidence only; production requires an owner-approved recovery policy and stronger distributed abuse controls.
